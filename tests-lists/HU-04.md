# HU-04: Publicar pérdida

Caso 1:
Validación de campos obligatorios
- Si falta categoría, título, descripción o fecha.
- Si alguno de estos campos está vacío o contiene solamente espacios.
- Si no se proporcionan datos.

-> "Completa categoría, título, descripción y fecha".

Caso 2:
Categorías de la pérdida
- Si se selecciona OBJETO o MASCOTA -> Aceptar la categoría.
- Si se selecciona OTRO y se especifica su categoría -> Aceptar.
- Si se proporciona una categoría desconocida -> "Selecciona OBJETO, MASCOTA u OTRO".

Caso 3:
Texto libre para la categoría Otro
- Si se selecciona OTRO y el texto de categoría está ausente, vacío o contiene solamente espacios -> "Especifica la categoría al elegir Otro".
- Si se selecciona OTRO y se proporciona un texto válido -> Aceptar.
- Si se selecciona OBJETO o MASCOTA -> No exigir el texto de otra categoría.

Caso 4:
Fecha existente y formato correcto
- Si la fecha no tiene el formato YYYY-MM-DD.
- Si el día o el mes no existen.
- Si se ingresa 29 de febrero en un año no bisiesto.
- Si se ingresa el año 0000.

-> "Ingresa una fecha válida".

- Si la fecha corresponde al 29 de febrero de un año bisiesto y no es futura -> Aceptar.

Caso 5:
Fecha de la pérdida no futura
- Si la fecha es posterior al día local actual -> "La fecha de la pérdida no puede ser futura".
- Si corresponde a hoy o a un día anterior -> Aceptar.
- Si se publica al final del día -> Seguir aceptando la fecha de ese mismo día.

Caso 6:
Cantidad y formato de las fotos
- Si no se proporcionan fotos, la lista está vacía o el valor no es una lista -> "Añade al menos una foto".
- Si se proporciona una foto válida -> Aceptar.
- Si se proporcionan varias fotos JPEG, PNG o WebP no vacías -> Aceptar.
- Si alguna foto es nula, tiene tamaño cero o corresponde a un formato no admitido -> "Usa fotos JPEG, PNG o WebP que no estén vacías".

Caso 7:
Al menos un medio de contacto
- Si correo y WhatsApp están ausentes, vacíos o contienen solamente espacios -> "Ingresa al menos un medio de contacto: WhatsApp o correo electrónico.".
- Si se proporciona solamente un correo válido -> Aceptar.
- Si se proporciona solamente un WhatsApp válido -> Aceptar.
- Cada contacto es opcional si se proporciona el otro; si se proporciona, debe ser válido.

Caso 8:
Formato del correo y de WhatsApp
- Si el correo proporcionado tiene formato incorrecto -> "El correo electrónico no es válido".
- Si el correo tiene espacios en los extremos -> Validar el valor sin esos espacios.
- Si WhatsApp contiene letras, varios signos +, una cantidad de dígitos no admitida o comienza con cero -> "Ingresa WhatsApp con código de país, por ejemplo +59171234567".
- Si WhatsApp incluye código de país y separadores admitidos -> Aceptar.

Caso 9:
Ubicación opcional mediante Google Maps
- Si no se proporciona ubicación -> Aceptar.
- Si se proporciona una dirección, coordenadas o un enlace HTTPS admitido de Google Maps -> Aceptar.
- Si el enlace pertenece a otro sitio o utiliza un esquema no admitido -> "Usa una dirección, coordenadas o un enlace de Google Maps".
- Al preparar la publicación, se debe guardar el texto sin espacios en los extremos y generar el enlace correspondiente.
- Si no hay ubicación -> Guardar texto y enlace vacíos.

Caso 10:
Preparación de la pérdida válida
- El tipo de publicación debe ser PERDIDA.
- El título y la descripción deben guardarse sin espacios en los extremos.
- Se debe conservar la fecha y copiar la lista de fotos sin reutilizar el mismo arreglo recibido.
- El estado debe ser "Pendiente de revisión".
- Si se selecciona OTRO -> Guardar categoriaOtra sin espacios en los extremos.
- Si se selecciona OBJETO o MASCOTA -> Guardar categoriaOtra vacía aunque se haya recibido un texto anterior.
- Normalizar WhatsApp y generar su enlace directo.
- Generar el enlace mailto: para el correo proporcionado.
- Si un contacto no se proporciona -> Su enlace debe quedar vacío.

Caso 11:
Rechazo de una pérdida inválida
- Si los datos incumplen una validación -> Devolver el mensaje correspondiente.
- No se debe crear el objeto publicacion.

Caso 12:
Guardar una pérdida con su foto
- Subir la foto mediante el servicio de Cloudinary.
- Guardar la URL devuelta, los datos de la publicación y la fecha del servidor en la colección perdidas de Firestore.
- Devolver la publicación guardada con su identificador.

Caso 13:
Guardar múltiples fotos
- Si se proporcionan varias fotos -> Subir cada una.
- Guardar todas las URLs devueltas en el mismo orden de las fotos recibidas.

Caso 14:
Estado pendiente al persistir
- Si se recibe una publicación con estado "Aprobado" u otro estado -> Guardarla como "Pendiente de revisión".

## Subida de fotos a Cloudinary

Caso 15:
Subida correcta de una foto
- Enviar el archivo y el upload_preset al endpoint del Cloud Name configurado.
- Si Cloudinary responde correctamente y proporciona secure_url -> Devolver la URL HTTPS de la foto.

Caso 16:
Rechazo de Cloudinary
- Si Cloudinary responde con error, por ejemplo "Upload preset not found" -> Propagar el mensaje de error.
- No devolver una URL como si la subida hubiera sido exitosa.

Caso 17:
Respuesta sin URL segura
- Si Cloudinary responde sin secure_url o sin una URL HTTPS -> "Cloudinary no devolvió una URL segura para la foto.".

Caso 18:
Tiempo máximo de subida
- Si una subida supera 45 segundos -> Cancelar la solicitud.

-> "La subida de la foto tardó demasiado. Inténtalo de nuevo.".
